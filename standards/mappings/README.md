# 标准映射目录与版本规范

本目录保存标准到软件业务规则之间的人工映射、审核证据和决策引用。**不参与程序运行，不是发布规则数据源。**

入口：[映射总索引](INDEX.md) · [标准映射表模板](templates/标准映射表模板.md) · [根目录治理](../../AGENTS.md) · [标准问题台账](../../STANDARD_ISSUES_REGISTER.md)。

## 1. 目录与命名

```text
standards/mappings/
├── README.md                     # 本目录规范
├── INDEX.md                      # 映射唯一总索引
├── templates/
│   └── 标准映射表模板.md
├── GB16780-2021/
│   ├── README.md                 # 现行批准版与历史材料入口
│   ├── 标准映射表_V1.2_修订稿.md  # 既有冻结文件，原名原位保留
│   ├── 标准映射表_V1.1_修订稿.md
│   ├── 标准映射表_用户原稿_V1_待复核.md
│   ├── 审核报告_20261011.md
│   └── DECISIONS_NEEDED.md
└── GB29446-2019/
    ├── README.md                 # 现行批准映射入口与采用边界
    └── 标准映射表_2026-10-18_已批准.md
```

- 一个标准年代版本一个目录，沿用 `GB16780-2021`、`GB29446-2019`；GB/T、行业标准等新目录采用不含空格或斜杠的稳定名称，例如 `GBTxxxxx-年份`，在入口写出正式标准号及既有程序 ID。不得借命名规范修改程序 ID。
- 多产品、多工序仍归同一标准目录；行业可作为索引分类，不再按行业复制文件。篇幅过长可按章节拆分，由标准 README 给出完整阅读入口。
- 新年代版本另建目录并记录替代关系，旧版不覆盖。目录不会因标准废止而删除。
- 新映射采用 `标准映射表_V1.0_草稿.md` 等明确版本名；批准时可保持文件名，以入口和正文批准记录明确实际状态，不靠文件名或“版本号最大”判断现行版。
- 材料增多后可按需使用 `originals/`、`reviews/`、`history/`；不预建空目录，不批量迁移已有引用。水泥现有文件全部保留原路径。
- 仓库文件使用相对链接；不得把某台电脑的盘符写成跨机器固定入口。

## 2. 唯一入口与版本管理

1. `INDEX.md` 负责发现标准与现行映射，标准目录 `README.md` 负责该标准详细导航。两处现行版本必须一致。
2. 每个标准版本最多一个现行批准映射；尚未批准或尚未补建时明确写“无”，不能用草稿补位。
3. 原稿、审核稿、批准稿分清身份；历史材料注明“历史，仅供追溯”。历史报告中的当时结论不覆盖现行批准版。
4. 新版本批准后，同一变更更新索引、标准入口、替代关系和批准证据；旧版本保留。普通修订通过 Git 追踪，不另存大量“最终版/最终修订版”。
5. 已冻结映射按自身变更约束办理；不得为迁就现有 JSON、代码、UI 或测试而反改已批准业务结论。水泥以 [V1.2 第0节](GB16780-2021/标准映射表_V1.2_修订稿.md) 为准，包含移动、重命名与文字修复约束；选煤以 [批准版](GB29446-2019/标准映射表_2026-10-18_已批准.md) 原字节归档，修改业务语义须说明证据和影响、经 Owner 明确批准后独立出新版本。

## 3. 两类状态分开记录

**文档维度**记录：是否已有完整映射、文档版本、草稿/已审核/已批准情况、批准日期和证据。`MAPPING FROZEN` 表示已批准业务映射冻结，不是新增的软件支持状态，也不是中央 Frozen Contract。

**软件维度**继续使用中央五种状态：`CATALOG_ONLY` / `MAPPING` / `READY_FOR_IMPLEMENTATION` / `IMPLEMENTED` / `SUPPORTED`。必须有设计、实现和验收证据，不因映射批准、目录建成或已有 JSON 而跳级。

总索引仅作导航和有日期的摘要；当前产品阶段、支持范围仍以 [TASK_STATE](../../TASK_STATE.md)、[唯一总体路线](../../参考标准开发路线.md) 和实际验收依据为准。未统一登记五态的旧标准只链接既有状态，不在本目录整理中自行赋予新状态。现有其他标准规则处于**遗留待映射重审**治理状态：这是对工程基线的审查安排，**不是**第六种软件支持状态，也不等于断言每条旧规则已被证实错误。目录存在、可运行、旧测试通过或发布标记均不能代替批准业务映射。

## 4. 映射内容与证据

新建映射使用 [模板](templates/标准映射表模板.md)，至少覆盖标准元数据、来源、适用范围、统计边界、分类、字段及单位、参数和查表、公式、修正、判定、异常、不适用/无法判定、输出及来源定位。

- 关键映射项使用稳定编号，编号不复用；已经冻结的旧映射可继续用稳定章节定位，不为套模板改写正文。
- 新建映射可采用 `MAP-GB29446-2019-001` 一类编号；纯排版调整不改号，删除项保留退役说明，拆分项另编号并记录来源。此编号仅用于文档追踪，不替代程序Rule ID或Standard Issue编号。
- 逐项区分“标准原文事实”“技术判断”“软件决定”；给出条款/表/公式/页码及相关 Issue、实现和测试链接。
- 原文疑义先查根目录唯一 [标准问题台账](../../STANDARD_ISSUES_REGISTER.md)，再按其规则登记；标准目录只引用编号，不另立平行台账。软件设计取舍可写在决策文件，不为填表制造标准问题。
- 从已有实现补建映射时，代码只用于核对实现现状；标准事实与 Golden 预期须有独立来源。缺少证据标“待核”，不得反向宣布标准如此要求。
- UI、Word 和未来 Excel 的标准相关字段名、单位、选项、说明、结果名称与含义应来自各自现行批准映射；例外须有 Owner 明确特批及采用记录。三渠道尽量保持相同业务内容，布局、分页和展开方式可不同。运行时应采用映射导出的结构化机器定义，不解析 Markdown 形成判定。
- 跨标准共同软件结果标签“未达3级”的适用边界以[统一判定规范 §10](../../docs/统一判定规范.md)为准；各标准映射仍决定本标准的阈值、方向、适用性和汇总规则。
- 后续逐标准执行“批准映射 → 与旧实现的差异清单 → Stage B 设计 → Stage C 实现 → 独立 Golden → Stage D 验收”；现有 JSON 只用于差异对照，不作为映射的批准依据。历史结果和规则快照不自动重算。
- 模板不要求把标准全文转成用户字段；是否新增字段、功能或阻断条件由 Stage B 的最小必要性检查决定。

## 5. 与其他资产的分工

| 位置 | 职责 |
|---|---|
| `standards/mappings/` | 人工业务映射、审核、决策引用 |
| `data/definitions/` | 唯一可编辑机器定义源，现有 64 项（含迁入的 16 项 `draft`）；定义存在不证明业务正确或正式支持 |
| `data/delivery-scope.json` | 显式选择随包 48 项及唯一正式评价标准；不从目录项数或 `published` 标记推断支持范围 |
| `standards/development/scope-63/`、`scope-65/` | 只读历史快照，用于旧范围、替代关系、旧 schema 回归；不是发布输入，不得反向覆盖当前定义 |
| `src/`、`tests/`、`tests/golden/`、`docs/golden/` | 实现与验证证据，留在原位并链接 |
| `docs/governance/` | 接入设计、执行与验收等治理记录；映射入口链接相关报告 |
| `STANDARD_ISSUES_REGISTER.md` | 全仓唯一标准问题台账 |
| `knowledge/` | 专业解释，不能替代标准、映射或 Rule |

原始国家标准 PDF 按既有来源管理流程独立保管，不在本目录提交原文 PDF，不随软件分发。映射记录来源、取得方式、原文 SHA256 和条款定位；不能把原文文件名当作人人可访问的仓库链接。

## 6. 新增与维护检查

1. 查总索引及既有标准 ID，避免重复目录；建立标准入口，记录来源和替代关系。
2. 保存原稿（如有），按模板整理并审核映射，遵循 Stage A → B → C → D；批准后先建与遗留实现的差异清单，本目录不另造开发流程。
3. 批准新映射时更新总索引、标准入口、批准证据和历史关系；实现、测试、验收各自链接对应版本。
4. 提交前检查相对链接、唯一现行入口、状态证据、冻结文件保护和变更范围。纯导航变更无需运行计算全量回归；业务变更按相应治理规则验证。

新增标准的最小交付是“标准目录README＋有证据的映射草稿＋总索引登记”；存在已批准版时，应同时列出当前工作草稿与现行批准版，二者不可混淆。没有原稿或审核报告时不制造占位文件。批准记录至少可追踪到版本、日期、批准范围和PR/用户决定等证据。
