# 非程序员验收与 AI 软件开发教程

## 一、先理解当前版本是什么

当前交付的是 Windows 单机正式首版（后续标准修订仍需走确认流程）。

- 当前标准包含46项范围、702条当前指标；702条规则已在统一确认表中逐项同意发布；另附GB 29141-2012历史版本；其中7条原文缺级/非单调警告仍应在业务使用时留意。
- 当前正式包版本为 `2026.09-published.1`，已完成规则确认，可进行正式合规判定；未来标准和旧标准手动选择时会显示提示。
- 当前开发基线为 `standards/development/scope-63`，共63项标准定义，其中46项已发布、17项仍为草案；`standards/development/scope-65` 仅作历史对照，禁止作为发布入口。草案须完成原文复核和确认表确认后才能发布。
- 因此当前最重要的工作不是“随便输入一个数看结果”，而是先确认标准规则和计算结果是否与原文一致。

## 二、你不需要安装 Python

验证时只使用：

1. `UEBench-0.1.0-win-x64.zip`：运行包。
2. `单位产品能耗对标导入模板.xlsx`：固定录入模板。
3. `统一标准规则确认表.xlsx`：标准规则确认表，共702条当前指标，702条均为“同意发布”，复核人和日期完整。
4. 对应的强制性标准原文 PDF：用于人工核对。

交付目录中另有 `验收助手.cmd`。不懂编程时可直接双击它：助手会核对运行包、安装程序和正式标准包的 SHA-256，检查确认表和导入模板是否存在，并在目录中生成 `验收结果-时间.txt`。确认表是允许填写的工作文件，填写或保存后哈希变化会标记为“已修改（允许）”，不会被误报为交付损坏。助手不会替代标准原文核对，也不会修改规则或数据库。

交付目录中的 `SHA256SUMS.txt` 用于确认文件没有在复制或传输过程中损坏。以运行包为例，在文件所在文件夹空白处打开 PowerShell，执行：

```powershell
Get-FileHash .\UEBench-0.1.0-win-x64.zip -Algorithm SHA256
```

将输出的 Hash 与 `SHA256SUMS.txt` 中同名文件的值逐字比较；不一致时不要解压或安装，先重新复制文件。

不要直接双击 `.uebench` 文件；它是标准数据包，不是软件程序。

## 三、第一次启动验证

1. 在 Windows 10/11 上新建一个空文件夹，例如“能耗软件测试”。
2. 将运行包复制进去并解压。
3. 进入解压后的 `UEBench` 文件夹，双击 `UEBench.exe`。
4. 如果 Windows Defender 弹出提示，先确认文件来源是本次交付包，再允许运行。
5. 首页应能看到标准包版本和标准数量；新建评价默认按电脑真实日期筛选正在生效的标准。
6. 打开“标准库”，应看到当前已发布标准；新版 GB 29141-2024 已纳入正式包，旧标准和未来标准可以手动选择，软件会先显示提示。

注意：不要安装旧的 candidate 候选包。应安装 `initial-standard-package-published.uebench`，并在首页确认版本为 `2026.09-published.1`。若“新建评价”为空，再检查标准包是否安装成功。

这一步只验证“程序能启动、数据库能建立、标准包能载入”，还没有验证标准数值是否正确。

## 四、最小功能验收

### 1. 直接录入

完成首批规则确认并安装 `published` 标准包后，再使用确认表中一个首批标准的测试案例：

1. 新建评价。
2. 选择标准、产品/工序和评价日期。
3. 选择“直接录入”。
4. 输入一个实际值和标准要求的单位。
5. 点击计算。

检查结果是否同时显示：实际值、基础限额、修正后限额、单项等级、原文页码/条款。

### 2. 明细计算

使用同一个案例改选“明细计算”：

1. 输入能源名称、能源量、单位、折标系数和分摊比例。
2. 输入合格产品产量和折算系数。
3. 点击计算。
4. 用计算器手工计算：

   `单位产品能耗 =（输入能源折标量 - 输出能源折标量）× 分摊比例 ÷ 合格产品产量`

5. 软件计算值与手算值应一致。
6. 在相同实际值下，直接录入和明细计算的等级应一致。

### 3. 边界值测试

对每个指标至少测试六个值：

- 等于 1 级限额；
- 1 级与 2 级之间；
- 等于 2 级限额；
- 2 级与 3 级之间；
- 等于 3 级限额；
- 超过 3 级限额。

等于限额时应达到该等级。缺少必填条件、单位错误、产量为零时，应显示“不完整”或错误提示，而不是猜测结果。

## 五、如何核对标准是否有效

对每个指标建立一张人工核对表，至少填写：

| 核对项 | 软件显示 | 标准原文 | 是否一致 |
|---|---|---|---|
| 产品/工序名称 |  |  |  |
| 指标名称 |  |  |  |
| 单位 |  |  |  |
| 1级限额 |  |  |  |
| 2级限额 |  |  |  |
| 3级限额 |  |  |  |
| 修正系数/公式 |  |  |  |
| 条件和适用范围 |  |  |  |
| 页码、条款、表号 |  |  |  |

核对顺序固定为：标准修改单/勘误 → 强制性标准原文 → 目录 → 汇编。汇编只能帮助找数据，不能覆盖原文。

只要有一项限额、单位、条件或公式无法在原文定位，就在确认表中选择“退回修改”，不要选择“同意发布”。

## 六、Excel 验收

1. 从“Excel导入”页面或交付文件中打开固定模板。
2. 不要改工作表名称、列名称或模板版本。
3. 填写一个完整案例并保存。
4. 导入时故意制造三种错误：缺少必填值、单位错误、产量为零。
5. 软件应指出工作表、单元格和错误原因，且错误数据不能部分入库。
6. 对成功计算的记录导出 Excel。
7. 将导出文件中的实际值、限额、等级和计算过程与软件界面逐项比较。

## 七、怎样记录问题

每个问题都记录以下信息：

- 软件版本；
- 标准编号和产品/工序；
- 评价日期；
- 输入模式；
- 输入数据或 Excel 文件；
- 软件结果截图；
- 标准原文页码/条款/表号；
- 你认为正确的结果；
- 复现步骤。

不要只说“结果不对”，否则无法定位是输入、单位、标准口径还是程序错误。

## 八、如何用 AI 参与软件开发

AI 最适合做四类工作：读取和整理资料、编写代码、编写测试、解释错误。AI 不应直接替你决定标准口径；标准原文和人工复核仍是最终依据。

### 推荐工作循环

1. 先写清楚目标：标准编号、产品、指标、输入、公式、输出和验收条件。
2. 让 AI 先阅读项目结构和现有规则，不要一开始就让它“大改全部代码”。
3. 每次只要求一个小变更，例如“增加单位校验”或“增加一个边界测试”。
4. 要求 AI 同时修改代码和测试。
5. 运行测试，保存结果。
6. 让 AI 解释失败原因，再决定是否接受修改。
7. 通过测试后再进入下一项。

### 可直接复制的提示词

**让 AI 规划功能**

> 你是本项目的技术负责人。请先阅读项目结构和执行规划，只输出实现方案、涉及文件、数据迁移风险和测试方案，不要修改文件。功能是：……

**让 AI 录入一项标准**

> 请根据提供的强制性标准原文，只提取 GB XXXXX-XXXX 中产品/工序、指标、单位、1/2/3级限额、适用条件、公式和页码。每个字段必须附原文页码/条款/表号；无法确定的字段标记为“待人工确认”，不要猜测，不要引用推荐性标准。

**让 AI 写测试**

> 为这个指标生成等于1级、1/2级之间、等于2级、2/3级之间、等于3级、超过3级、缺失值、非法单位、除零和实施日前日期测试。使用 Decimal，不使用 float。先列出测试案例，再修改测试文件。

**让 AI 排查错误**

> 以下是完整错误信息、输入数据、期望结果和实际结果。请先判断问题属于输入、单位、规则数据、计算引擎、界面还是导出层；给出证据和最小修复方案，不要直接重写无关代码。

**让 AI 做代码审查**

> 请审查本次变更是否违反以下约束：不得使用 float 参与限额比较；不得使用 eval；历史结果不得被标准包升级改写；只有 published 规则可正式计算；Excel 不得建立第二套判级逻辑。请按严重程度列出问题和测试建议。

## 九、非程序员使用 AI 的安全原则

- 不把“AI说可以”当作标准依据。
- 不接受没有测试、没有原文页码的规则。
- 不让 AI 一次性重写整个项目。
- 每次修改前备份项目和数据库。
- 让 AI 给出变更文件清单、测试结果和未解决风险。
- 重要数据、企业数据和未公开标准原文不要上传到不受控的平台。
- 正式发布前，必须由懂标准的人确认规则表。
