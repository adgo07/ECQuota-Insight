# 统一判定规范

状态：**Numeric Contract v1 已正式采用**。  
中央冻结基线：`Qingzhou-contracts@ee5feb0cc34dbd99790500fadd0c4c932e202a20`  
项目 Numeric Profile：`ECQUOTA_DECIMAL_FULL_VALUE_V1`

本文件规定 ECQuota 当前正式 Numeric 判定语义。标准原文或更具体的正式 Rule 如有明确数值处理要求，优先按该标准/Rule 表达；历史软件行为本身不是业务依据。

## 1. 正式判定与显示分离

正式数值链：

```text
原始十进制输入
→ normalized Decimal
→ authoritative calculation value
→ comparison value
→ formal comparison
→ grade / result
```

默认情况下：

```text
comparison value = full calculation value
```

显示链独立：

```text
calculation value
→ display formatting / display rounding
```

显示位数、格式化字符串和 UI 展示值不得反向进入正式计算或正式比较。

## 2. 默认 formal comparison

ECQuota 公共 Engine 的默认正式业务比较是：

```text
full-value exact comparison
```

允许的普通比较包括：

```text
<
<=
==
>=
>
```

默认不增加 epsilon，不在比较前自动 ROUND6，不因显示位数或历史软件习惯改变 comparison value。

## 3. ROUND6 已从公共正式判定链移除

历史实现曾对 actual 和 threshold 统一执行：

```text
ROUND(value, 6)
ROUND_HALF_UP
```

再进行 grade/compliance 比较。

该行为属于 **legacy implicit rounding**。在无标准/Rule 明确依据时，它不再是 ECQuota 正式业务语义。

Numeric Contract v1 Full Adoption 后：

- 公共 `_grade()` 使用 Decimal 全值直接比较；
- compliance 使用 Decimal 全值直接比较；
- `_round_threshold_value()` / 全局 six-place comparison helper 已从生产判定链移除；
- 已发布 `data/definitions/*.json` 当前 `round_places` 使用数为 `0`；
- 不再保留“其他标准先暂时默认 ROUND6”的兼容分支。

因此：

> **没有 explicit rounding Rule，就不修约，直接 full-value comparison。**

## 4. Rounding 分类

### 4.1 Working rounding

ECQuota 项目 Profile 当前声明：

```text
working_precision = 28
rounding_mode     = ROUND_HALF_EVEN
```

该配置用于有限精度 Decimal 算术，不自动变成业务修约规则，也不定义显示修约。

authoritative evaluation 在 Profile 自己的 Decimal context 中运行，caller 的外部 Decimal ambient context 不得静默改变正式结果。

### 4.2 Explicit business rounding

只有标准原文或正式 Rule 明确要求修约时才允许。

Rule 必须至少声明：

- stage；
- places / precision / significant digits（按适用项）；
- rounding mode；
- purpose；
- source/provenance。

当前 Rule 模型保留 explicit rounding 能力，但已发布标准目前没有 `round_places` 实例。

### 4.3 Display rounding

仅用于 UI、报告和导出。

不得反馈正式 calculation/comparison。

### 4.4 Implicit rounding

默认禁止，包括：

- 无来源的 pre-comparison `round()` / `quantize()`；
- 为兼容旧结果而隐藏修约；
- 先按显示位数格式化再用于比较；
- 为掩盖精度问题而引入隐藏 rounding。

## 5. Tolerance

ECQuota 当前正式业务边界默认：

```text
business tolerance = none
```

禁止 platform/global epsilon。

如未来标准明确规定 tolerance，必须保留来源、单位、应用阶段与方向语义；算法/测试数值 tolerance 不得偷换为正式业务边界 tolerance。

## 7. GB 29446 breaking behavior

GB 29446—2019 未发现要求等级比较前统一 ROUND6 的条文，因此正式判级使用 Decimal full-value comparison。

以下旧结果属于 intentional numeric behavior change：

| Exact value | Legacy ROUND6 | Full-value |
|---|---|---|
| `5.0000004` | 1级 | 2级 |
| `7.0000004` | 2级 | 3级 |
| `8.5000004` | 3级 | 未达标 |
| `2.0000004` | 1级 | 2级 |
| `3.0000004` | 2级 | 3级 |
| `4.5000004` | 3级 | 未达标 |

原 N01-A legacy assertions 继续作为 strict XFAIL migration evidence 保留；新正式期望由 Frozen Numeric v1 Conformance 和 N01-A regression evidence 验证。

## 8. Excel / openpyxl authoritative ingress

真实测试已经证明：

```text
XLSX numeric cell
→ openpyxl
→ Python binary float
```

可能丢失原始十进制 lexical value，并且可以跨越正式等级边界。例如 XLSX XML 中的：

```text
5.0000000000000001
```

可被 openpyxl 物化为：

```text
5.0
```

对 GB 29446 边界，这可能把本应为 2 级的精确值错误变成 1 级。

因此当前项目采用最小安全规则：

- authoritative XLSX 数值单元格如被 openpyxl 读成 Python `float`，导入必须报错；
- 模板正式数值列使用文本格式；
- 用户以十进制 lexical text 录入正式数值；
- 不再允许 `float → str → Decimal` 静默成为 authoritative business value。

中央统一 lossless XLSX numeric-cell interchange scheme 仍为 OPEN；本项目不声称已经冻结公共 Excel schema。

## 10. 其他业务原则

- 指标未满足标准最低等级/限定值时输出“未达标”；缺少必需数据仍为“不完整”，确实不适用仍为“不适用”。
- 企业属性不改变 GB 29446 的指标等级；准入或建设属性提示与等级结论分离。
- authoritative Domain 不接受 Python binary float；正式输入应保持可追溯的十进制语义。
- 历史评价不自动重算，保留当时结果、规则快照和计算轨迹。
- 未来某标准如明确要求显式修约，应建立 Rule-level explicit rounding，不得重新启用全局 ROUND6。
